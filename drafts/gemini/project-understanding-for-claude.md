## (1) SHARAY's Intended End-to-End Purpose & Authorized Lifecycle Stages

SHARAY is an educational and defensive open-source security assessment, vulnerability verification, and bug-bounty workbench (`READ MAIN_PROMPT.txt:1-66`, `READ MAIN_PROMPT.txt:140-163`, `READ MAIN_PROMPT.txt:464-551`). Its goal is to give an operator or security researcher a single, auditable environment that supports **manual control**, **AI-assisted investigation**, and **bounded automated execution** strictly inside an explicitly authorized `ScopePolicy` (`READ packages/security_policies/__init__.py:1-120`).

Rather than stopping at noisy unverified scanner alerts, the human (`shardul`) directed that SHARAY cover the full **8-Stage Authorized Assessment & Verification Lifecycle** (`READ drafts/gemini/validation-and-session-architecture.md:1-120`):

1. **Scope & Authorization Gate**: Operator defines a target and `ScopePolicy` (`hosts`, `allowed_origins`, `allowed_paths`, `excluded_paths`, `allowed_cidrs`, `starts_at`, `expires_at`, `authorized_by`) (`READ aegis/api.py:562-568`, `READ packages/security_policies/__init__.py:35-95`). Every action is evaluated by `evaluate_tool_action(action, metadata, readiness)` (`READ packages/shared_schemas/__init__.py:290-366`).
2. **Stage 1 — Detection & Multi-Tool Ingestion**: Built-in `safe_http` (`READ packages/scanner_adapters/__init__.py:83-125`), third-party scanners (`nmap`, `zap`, `nuclei`, `semgrep`, `gitleaks`, `metasploit.catalog`), and source/dependency/OpenAPI analyzers (`READ services/source_analysis_worker/__init__.py:1-90`, `READ packages/scanner_adapters/integrations/osv.py:1-90`, `READ packages/scanner_adapters/integrations/openapi.py:1-90`) produce sanitized `Observation` and `Finding` records (`status="suspected"` or `"needs_triage"`).
3. **Stage 2 — Technical Validation & Correlation**: Candidate findings are correlated with non-destructive validation techniques across 10 vulnerability classes (`sql_injection`, `xss`, `ssrf`, `xxe`, `command_injection`, `auth_bypass`, `access_control`, `server_side`, `client_side`, `api_vulnerability`) (`READ drafts/gemini/metasploit_and_validation_catalog.py:34-156`).
4. **Stage 3 — Controlled Verification Execution**: Approved, scope-checked verification probes or `metasploit.approved_auxiliary` checks run within `ExecutionBudget` (`max_requests`, `max_seconds`, `max_concurrency=1`) and record preconditions, request/response evidence hashes, and whether the flaw is `confirmed_reproducible` vs `suspected` vs `validation_failed` (`READ drafts/gemini/codex_c4_c6_persistence.py:46-71`).
5. **Stage 4 — Bounded Diagnostic Session Lifecycle**: Where an authorized validation establishes an authenticated or diagnostic session (HTTP session, read-only SQL catalog session, or bounded Metasploit session), SHARAY tracks session state (`opening`, `active`, `degraded`, `expired`, `terminated`, `cleaned_up`), lease expiry (`ttl_seconds`), and exact `duration_seconds` (`READ drafts/gemini/codex_c4_c6_persistence.py:74-96`, `READ drafts/gemini/validation_session_engine.py:125-245`). This is bounded diagnostic session management within the engagement window — never covert persistence or unrestricted access (`READ MAIN_PROMPT.txt:474-480`).
6. **Stage 5 — Post-Verification Boundary Assessment**: Within a diagnostic session, only allowlisted read-only boundary checks run (privilege/execution-context identity, accessible resource inventory, cross-tenant permission boundary verification, and non-sensitive data-exposure metadata counts with secret redaction) (`READ drafts/gemini/validation_session_engine.py:248-310`).
7. **Stage 6 — Three-State Impact Calibration & Adversarial Review**: An exploit or validation succeeding never automatically sets maximum severity (`READ MAIN_PROMPT.txt:544-551`). SHARAY records `theoretical_impact`, `observed_impact`, and `not_yet_tested` separately (`READ drafts/gemini/codex_c4_c6_persistence.py:99-119`), and in AI-assisted mode an independent Challenger / `verifier` checks observation SHA-256 provenance and reasoning flaws before a `supported` hypothesis can reach `confirmed` (`READ services/ai_analysis_worker/__init__.py:50-65`, `READ drafts/gemini/ai_verifier_and_adversarial_review.py:91-209`).
8. **Stage 7 & 8 — Controlled Cleanup Verification & Cryptographically Verifiable Reporting (`sharay.provenance.v1`)**: Any test markers or session state are removed and verified (`verified_clean`), and `render_report()` exports HTML/Markdown/JSON/PDF bug-bounty and assessment reports containing root cause, session duration (`duration_seconds`), 3-state impact breakdown, cleanup status, and a tamper-evident `sharay.provenance.v1` SHA-256/HMAC manifest (`READ packages/reporting/reports.py:164-342`, `READ drafts/gemini/report_provenance.py:45-330`).

## (4) Where L1–L8 (Claude) and C1–C8 (Codex) Are Likely to Disagree or Double Up

1. **Finding Schema & Severity/Status Vocabulary Mismatch (`READ aegis/models.py:117-135` vs. `READ packages/scanner_adapters/integrations/zap.py`, `nuclei.py`, `gitleaks.py`)**:
   - Codex's `Finding` table requires `category`, `severity`, `confidence`, `status`, `description`, `remediation`, `affected_url`, `fingerprint` (`READ aegis/models.py:124-132`).
   - Your L3 parsers intentionally return tool-specific dicts: `gitleaks.parse` returns `{"rule", "file", "line", "fingerprint"}` (no `severity`, `confidence`, or `affected_url`); `nuclei.parse` returns `{"template", "name", "severity", "matched_at", "matcher", "fingerprint"}` (where `severity` can be `"unknown"`); `zap.parse` returns `risk` instead of `severity`.
   - *Risk*: If both halves assume the other translates parser dicts into `Finding` rows, either neither builds the translator or both build incompatible translators. A single normalization mapper in `packages/scanner_adapters/integrations/` is needed.
2. **Secret Redaction Placeholder & Key-Rule Divergence (`READ packages/reporting/reports.py:14-111` vs. `READ services/update_worker/__init__.py` & `services/source_analysis_worker/`)**:
   - Codex's `packages.reporting.redact` replaces secret values with `"[REDACTED]"` and **also** wipes any dict value whose key matches `_SECRET_KEY` (`password|secret|token|authorization|cookie|credential|api_key`, `READ packages/reporting/reports.py:15-20`).
   - Note that any dict key containing `_token_` (such as `cancellation_token_ref` in `ProposedToolAction` / `ExecutionReadiness`, `READ packages/shared_schemas/__init__.py:109,232`) will have its value overwritten to `"[REDACTED]"` if passed through `packages.reporting.redact()`!
3. **1 MiB Runner Output Cap vs. 10 MiB Parser Budget (`READ docs/integrations/TOOL_REPORTS.md:18,32`)**:
   - Your parsers in `_parsing.py:18` allow `MAX_REPORT_BYTES = 10 * 1024 * 1024` (10 MiB), but `services/scanner_worker` caps stdout at 1 MiB (`READ docs/integrations/TOOL_REPORTS.md:32`), and `packages/shared_schemas/__init__.py:98` defaults `ExecutionBudget.max_evidence_bytes` to `65536` (64 KiB, max 1 MiB). Any tool writing reports to stdout over 64 KiB–1 MiB will be truncated by the runner and then rejected as invalid JSON by `load_json()`. Writing tool output to a file inside the per-run scratch directory avoids stdout truncation.
4. **Live-Target Loopback vs. CIDR/Hostname Scope (`READ packages/scanner_adapters/__init__.py:127-145` vs. `READ packages/security_policies/__init__.py`)**:
   - Codex updated `packages/security_policies/__init__.py` in the working tree to support CIDR and DNS-pinned live targets (`live_destination_egress`), whereas `packages/scanner_adapters/__init__.py:101` (`safe_http`) and `apps/web/app/api.ts:89` (`laboratoryScope`) still hardcode `127.0.0.1` / `[::1]` in several places. Your L1 runner (`services/scanner_worker`) and L3 network tools (`nmap`, `nuclei`, `zap`) must consume the resolved numeric `Destination(ip, port)` from `packages.security_policies` so DNS rebinding between policy check and tool execution is impossible.
