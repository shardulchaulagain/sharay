## 1. Executive Summary

A targeted hostile attack pass was performed against the Nmap network inventory adapter (`packages/scanner_adapters/integrations/nmap.py`) and the dependency inventory reader (`services/source_analysis_worker/dependencies.py`).

The security posture of both modules is generally robust:
- `build_argv` in `nmap.py` strictly restricts arguments: only literal canonical IP addresses without netmasks or hostnames are accepted, port lists reject booleans and non-integers, rates and timeouts are strictly bounded, and no script flags (`--script`) can be injected.
- `dependencies.py` avoids executing subprocesses (`pip`, `npm`), strictly enforces regular file descriptors with `O_NOFOLLOW | O_NONBLOCK`, rejects directory symlink traversal, catches `RecursionError` on nested JSON trees, and redacts credentials from repository URLs and pip option arguments.

However, four concrete defects were uncovered:
1. **Uncaught `OverflowError` in Nmap XML parser** (`nmap.py` line 100): An oversized `start` timestamp attribute causes `datetime.fromtimestamp()` to raise `OverflowError`. Because `inventory()` only catches `ValueError` and `OSError`, this unhandled exception crashes the process.
2. **Uncapped / Duplicate Port Observation Explosion** (`nmap.py` line 111): `parse_xml` checks `number in ports` but lacks deduplication. Adversarial XML with repeated `<port>` tags explodes into thousands of observations, bypassing the `MAX_PORTS = 100` restriction.
3. **CRLF Line Continuation Dropping Valid Dependencies** (`dependencies.py` line 62): `_requirements()` uses `text.replace("\\\n", " ")` which strictly expects UNIX LF newlines. Requirements files with Windows CRLF (`\r\n`) line continuations (common in hash-pinned manifests generated by `pip-tools`) fail to merge, causing pinned packages to be dropped into `unresolved`.
4. **Dual-Stack / Extraneous Address Mismatch False Rejection** (`nmap.py` line 109): If an Nmap XML reports both IPv4 and IPv6 addresses for a target, `reported != {ipaddress.ip_address(address)}` triggers a `ValueError` failure rather than verifying that the requested address is present and target-bound.

## 2. Vulnerability Details & Reproductions

### Defect 1: Unhandled `OverflowError` on Oversized Nmap `start` Attribute
- **Location**: `packages/scanner_adapters/integrations/nmap.py`, line 100
- **Evidence**:
  ```python
  start = root.get("start", "")
  captured_at = datetime.fromtimestamp(int(start), UTC).isoformat() if start.isdigit() else None
  ```
- **Vulnerability**:
  `start.isdigit()` is `True` for any sequence of ASCII digits regardless of length (e.g. `"99999999999999999999"`). `int(start)` succeeds. `datetime.fromtimestamp()` then raises `OverflowError: timestamp out of range for platform time_t`.
  In `inventory()` (line 204), the error handling block is:
  ```python
  except ValueError as exc: ...
  except OSError: ...
  ```
  In Python, `OverflowError` inherits from `ArithmeticError`, which does NOT inherit from `ValueError` or `OSError`. Consequently, the exception escapes uncaught, terminating the scan runner abruptly instead of recording a clean failure check.
- **Reproduction**:
  `test_nmap_timestamp_overflow_crashes_uncaught` in `drafts/gemini/attack-tests/test_attack_2.py`.
- **Proposed Fix**:
  ```python
  try:
      captured_at = datetime.fromtimestamp(int(start), UTC).isoformat() if start.isdigit() else None
  except (OverflowError, ValueError):
      captured_at = None
  ```

### Defect 2: Unbounded Duplicate Port Observation Explosion
- **Location**: `packages/scanner_adapters/integrations/nmap.py`, lines 111-137
- **Evidence**:
  ```python
  for port in host.iterfind("ports/port"):
      number = int(port.get("portid", ""))
      state = port.find("state")
      if number not in ports or port.get("protocol") != "tcp" or state is None:
          raise ValueError("nmap reported a port outside the request.")
      ...
      observations.append(...)
  ```
- **Vulnerability**:
  While `build_argv` restricts the requested ports to `1 <= len(ports) <= MAX_PORTS` (100), `parse_xml` does not track whether a port has already been added to `observations`. A crafted 1 MB XML document containing 10,000 `<port portid="80">` elements causes `parse_xml` to generate 10,000 observation records, flooding downstream consumers and report builders.
- **Reproduction**:
  `test_nmap_duplicate_port_explosion_uncapped` in `drafts/gemini/attack-tests/test_attack_2.py` (500 duplicate port tags yielded 500 observations).
- **Proposed Fix**:
  Track seen ports per host and reject or deduplicate:
  ```python
  seen_ports = set()
  for port in host.iterfind("ports/port"):
      number = int(port.get("portid", ""))
      if number in seen_ports:
          continue  # or raise ValueError("duplicate port in tool output")
      seen_ports.add(number)
  ```

### Defect 3: CRLF Line Continuation Breaks Valid Pinned Requirements
- **Location**: `services/source_analysis_worker/dependencies.py`, line 62
- **Evidence**:
  ```python
  for line in text.replace("\\\n", " ").splitlines():
  ```
- **Vulnerability**:
  In files using Windows CRLF line endings (`\r\n`), line continuations appear as `\\\r\n`. The substring `\\\n` does not match, so `text.replace("\\\n", " ")` does nothing. When `splitlines()` runs, the line is split into two fragments:
  1. `requests \`
  2. `    == 2.31.0`
  Neither fragment matches `_PINNED` or `_SPECIFIER`. Both lines are classified as `"unrecognized line"` and dropped into `unresolved`, resulting in zero packages detected from a valid pinned manifest!
- **Reproduction**:
  `test_requirements_crlf_line_continuation_broken` and `test_requirements_hash_continuation_crlf_broken` in `drafts/gemini/attack-tests/test_attack_2.py`.
- **Proposed Fix**:
  Normalize line endings before replacing line continuations:
  ```python
  normalized = text.replace("\r\n", "\n").replace("\r", "\n")
  for line in normalized.replace("\\\n", " ").splitlines():
  ```

### Defect 4: Hostile External Entity (XXE) and DoS Resilience Verification
- **Location**: `packages/scanner_adapters/integrations/nmap.py`, lines 86-95
- **Observation**:
  `parse_xml` enforces:
  ```python
  if len(data) > MAX_XML_BYTES:
      raise ValueError(...)
  if not data.startswith(_DECLARATIONS):
      raise ValueError(...)
  rest = data.replace(_DOCTYPE, b"", 1)
  if b"<!DOCTYPE" in rest or b"<!ENTITY" in rest:
      raise ValueError(...)
  ```
  Verified that:
  - Custom DOCTYPEs, external SYSTEM identifiers, and internal entity definitions are completely prevented.
  - Payloads exceeding 1 MB are rejected upfront before ElementTree instantiation.
  - Python's `xml.etree.ElementTree` is non-resolving for external entities by default.
